# Тестовый план СМП

Составлен на всю систему (см. `test-strategy.md`), с фокусом на ядро Authorization и Card Management.

## 1. Область тестирования

Объект — СМП (11 сервисов, PostgreSQL, RabbitMQ). В область входят: сервисы Authorization и Card Management (глубокий тест-дизайн) и периферийные сервисы (чек-листы, критический путь). Детализация покрытия — в `test-design.md` и `checklists.md`.

## 2. Критерии входа и выхода в тестирование

**Критерии входа:**
- `docker compose up -d` поднимает все 11 сервисов + PostgreSQL + RabbitMQ; все контейнеры Up (healthy)
- Smoke-чек-лист (раздел 1 `checklists.md`) пройден полностью
- Сгенерирован пул тестовых карт (≥ 20); вручную созданы карты редких статусов (INACTIVE, BLOCKED, EXPIRED) через PATCH
- ТЗ зафиксированы; неоднозначности вынесены в вопросы аналитику (`test-design.md`, раздел 7)

**Критерии выхода:**
- 100 % тест-кейсов ядра исполнены; ≥ 95 % Passed; каждое падение разобрано
- Попарный набор сгенерирован, каждая строка спроецирована в тест-кейс
- Открытых дефектов Critical/High — 0
- Чек-листы дыма и критического пути закрыты
- Покрытие требований ядра тест-кейсами — 100 % (матрица трассировки)


## 3. Как будем тестировать

Тестирование чёрного ящика на развёрнутой локально СМП: ручные проверки через REST API (curl/Postman) и сценарии симулятора терминалов; подготовка данных генератором карт и PATCH-запросами; негативные инфраструктурные сценарии — остановкой контейнеров (`docker compose stop card-management`).

**Риски и их обработка:**

| Риск | Вероятность | Влияние | Митигация |
|---|:---:|:---:|---|
| Неатомарность «проверить → зарезервировать» (race condition, допустимо по ТЗ) | Средняя | Высокое | Не гонять параллельные кейсы на одной карте |
| Таймауты Bin Lookup → fallback | Средняя | Среднее | Учитывать fallback в ожиданиях |
| Редкие статусы в генераторе (3 %/2 %) | Высокая | Низкое | Готовить статусы вручную PATCH |
| Flaky из-за start_period контейнеров | Низкая | Среднее | Ждать healthy; повтор ×2 перед вердиктом |

## 4. Какие техники тест-дизайна используем

Для ядра:
- **Классы эквивалентности** — для полей с одиночной зависимостью результата (статус карты, формат PAN, вид лимита)
- **Граничные значения** — тройки ON/OFF для лимитов, баланса, срока действия, пагинации
- **Попарное тестирование (pairwise)** — для независимых параметров авторизационного решения; модель PICT с ограничениями, генерация набора, проецирование строк в кейсы

Таблицы решений и диаграммы переходов состояний не входят в объём данного цикла; их применение запланировано на следующую итерацию.

## 5. Какие виды тестирования используем

Функциональное (компонентное + интеграционное + E2E критического пути) и дымовое (smoke). Регрессионное — при повторных прогонах после исправлений. Нагрузочное — отдельный цикл, вне рамок данного плана.

## 6. Критерии выполнения тестирования

- Каждый кейс исполнен и имеет фактический результат (passed/failed/blocked)
- Повторный прогон упавших кейсов после каждого исправления (регресс)
- Дефекты классифицированы по severity/priority; критические и высокие закрыты до сдачи
- Флаки-повторы: падение подтверждено дважды, прежде чем считаться дефектом

**Метрики:**
- покрытие требований ядра кейсами — 100 %
- % исполненных кейсов, % Passed
- дефекты по severity
- попарный набор: 5832 комбинации → 27 строк (все 222 пары)
- время smoke-прогона
