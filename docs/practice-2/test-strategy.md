# Тестовая стратегия СМП

## 1. Цель тестирования

Подтвердить корректность работы цикла авторизации транзакций: для каждого статуса карты (ACTIVE, INACTIVE, BLOCKED, EXPIRED) и каждой причины отказа (карта не найдена, истёк срок, лимиты, баланс, недоступность CMS) система выдаёт соответствующее решение и ответ — APPROVED/DECLINED с корректным responseCode ("00", "14", "51", "54", "61", "05", CARD_INACTIVE, CARD_BLOCKED) согласно `tz/04-authorization.md`. Дополнительно — корректность управления данными карт (CRUD, генерация, резервирование) по `tz/05-card-management.md` и работоспособность сквозной цепочки от терминала до дашборда.

## 2. Объект тестирования

СМП целиком (11 сервисов + PostgreSQL + RabbitMQ), с выделением ядра:

- **Authorization** — решение по транзакции: статусы карты, срок действия, дневной/месячный лимиты, баланс, резервирование, RRN/authCode
- **Card Management** — CRUD карт, генератор тестовых карт (Лун, статусы 95/3/2), резервирование средств, мягкое удаление
- Периферия: Gateway, Switch, Terminal Simulator, Merchant Simulator, Transaction Logger, Bin Lookup, Notification, Web Dashboard

## 3. Уровни тестирования

- **Модульное (компонентное)** — каждый сервис в изоляции: валидации входных данных, CRUD, статусная модель, decline-причины
- **Интеграционное** — связки Authorization ↔ Card Management (резервирование, лимиты), Authorization ↔ Bin Lookup (обогащение issuerId, fallback), Switch ↔ Transaction Logger (события)
- **E2E** — сквозные сценарии критического пути: покупка, отказы, блокировка/удаление карты, откат средств

## 4. Область тестирования

**Что входит:** функциональное поведение всех сервисов согласно ТЗ; response-коды авторизации; лимиты и баланс; CRUD и генерация карт; мягкое удаление; резервирование; сквозная цепочка.

**Что НЕ входит — и почему:**

- **UI/UX дизайн Web Dashboard** — проверяем только доступность и отображение данных; визуальная косметика не влияет на финансовую корректность
- **Нагрузочное тестирование** — отдельный цикл с собственными метриками и окружением; в рамках данного плана не выполняется
- **Криптозащита данных карт** (шифрование, токенизация PAN, маскировка номера) — в учебной СМП криптографические механизмы реализованы моками, реальный алгоритм не задан — проверять нечего
- **Аутентификация держателя карты: PIN, CVV, 3-D Secure** — по ТЗ Authorization реализованы стабами (PIN всегда 1234, CVV всегда 123, 3DS — заглушка); реальная проверка эмитентом не выполняется
- **Взаимодействие с реальными внешними системами** (банки-эмитенты, платёжные сети) — все внешние зависимости заменены симуляторами (Bin Lookup, Terminal/Merchant Simulator)
- **Отказоустойчивость инфраструктуры** (репликация PostgreSQL, кластеризация RabbitMQ) — гарантии среды, а не прикладного кода

## 5. Риск-ориентированный подход и приоритизация

Объём тестирования следует за риском. Максимальный риск — финансовая некорректность (ошибочное одобрение/отклонение, нарушение лимитов, потеря средств при резервировании/откате), поэтому ядро (Authorization, Card Management) покрыто полным тест-дизайном: классы эквивалентности, граничные значения, попарное тестирование (модель PICT с ограничениями). Периферия с простой логикой — smoke и критический путь: их отказы быстро вскрываются дымовыми проверками, глубокая модель не даёт сорразмерного эффекта.

Принципы приоритизации: 1) валидные сценарии раньше негативных; 2) денежные операции раньше нефинансовых; 3) частые статусы карт раньше редких (INACTIVE 3 %, BLOCKED 2 %); 4) границы классов раньше «середины».
